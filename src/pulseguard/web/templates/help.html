How PulseGuard works

Each monitor runs on its own interval, at least every 30 seconds. A result is stored even when you are not looking at this page.

An incident opens after K failures in a row. The default K is 3, and you can set it from 1 to 20 on the Alerts page. Further failures while it is open do not open a second incident.

An incident resolves after M successes in a row. The default M is 1. A success is counted even when another monitor this one depends on is down. A failure is not, so a shared outage stays attached to the monitor that failed first.

Every open and resolve is written to the alert log. If SMTP is not configured the status is "not configured". The log is how you see alerts without a mail server.

You type every monitor. Nothing is filled in for you. A defacement monitor can learn the SHA-256 of the first successful response, or you can type the hash. A heartbeat monitor shows its ping URL and token after you save it, with a button to copy each one.

The public status page reads stored results. It does not contact the monitored targets, and it does not show targets or tokens.

The same rules are written in docs/architecture.md and docs/security.md next to the program.

Check kinds

HTTP: did the address answer with the status you expect?

Keyword: does the visible page text include a phrase you chose?

Defacement: did the page bytes stay the same as the baseline hash?

TCP: does the port accept a connection?

DNS: does the name resolve to the addresses you listed?

TLS: will the certificate expire soon?

Heartbeat: did a job you run ping PulseGuard recently enough?

Glossary

DNS is the name that points at an address.

TCP is a connection to a port, with no web page involved.

TLS is the certificate that expires on a date.

A heartbeat is a ping from a job. If the ping stops, the job may have stopped.

An incident is K failures in a row. One failure is a down check, not yet an incident.
